# Repository Guidelines

## Project Structure & Module Organization

`app/` is the Android application module. Production Java sources are in
`app/src/main/java/com/zuoqirun/lyricscompanion/`; resources belong in
`app/src/main/res/` (including `layout-land/` for landscape overrides). Put
local JVM tests beside the matching package in `app/src/test/java/` and
debug-only helpers in `app/src/debug/`.

`update_server/` is an independent Node.js service for release metadata,
feedback, and update delivery; its tests live in `update_server/test/`.
`promo/` and `video/` contain promotional assets and tooling, not Android app
code. Keep generated APKs, Gradle outputs, server state, and `.env` files out
of Git as defined by `.gitignore`.

## Build, Test, and Development Commands

From the repository root on Windows:

```powershell
.\gradlew.bat :app:testDebugUnitTest :app:lintDebug --no-daemon
.\gradlew.bat :app:assembleDebug
adb install -r .\app\build\outputs\apk\debug\app-debug.apk
```

The first command runs JVM tests and Android lint; run it before proposing an
Android change as ready. The second builds an installable debug APK. Use
`cd update_server; npm test` for server tests, and `node --check server.js`
for a quick syntax check. Release builds require ephemeral `APP_SIGNING_*`
environment variables—never commit or print signing material.

## Coding Style & Naming Conventions

Follow the existing Java style: four-space indentation, braces on the same
line, `UpperCamelCase` classes, `lowerCamelCase` methods/fields, and
`UPPER_SNAKE_CASE` constants. Keep package names under
`com.zuoqirun.lyricscompanion`. Name tests `*Test.java` and describe behavior
clearly, for example `LrcTimelineTest`. Preserve UTF-8 for Chinese UI strings
and resource text. This app supports API 19: guard newer Android APIs and use
compatibility alternatives where needed.

## Testing Guidelines

Add or update a focused JUnit 4 test for parsing, layout, timing, or preference
logic changes. Avoid enabling `LiveEnhancedLyricTest` unless explicitly needed:
it is opt-in via `LIVE_LYRIC_TEST=1`. Static checks do not replace device
validation of overlays, permissions, listener recovery, or secondary displays;
state that distinction in change notes.

## Commits & Pull Requests

Recent commits use short imperative subjects, e.g. `Improve Kuwo car lyric
matching and session support`. Keep each commit scoped to one coherent change.
In this often-dirty worktree, stage explicit paths rather than `git add -A`;
do not include `secret.md`, APKs, captures, or unrelated promo/server work.
PRs should explain the user-visible effect, tests run, API/device risk, linked
issue when applicable, and screenshots or recordings for visual changes.

## Communication and Existing Work

Use Chinese when communicating with the maintainer. Read the current issue body
and comments, repository status, and applicable instructions before changing code.
Treat `CLAUDE.md` as a pointer to this file so the two tools share one source of
project guidance. Keep both tracked files in the repository.

This checkout may contain the maintainer's changes. Preserve unrelated edits and
untracked media. Use the existing suitable checkout, inspect branch ancestry, and
never reset or force-push to overwrite remote work. A local branch name alone is
not evidence of the destination: verify the exact remote ref after pushing.

## Release Channels and Issue Completion

Feature/test releases go to the exact `beta` branch when requested. Dispatch the
test release with `gh workflow run build-release.yml --ref beta -f channel=beta`.
A push to `main` touching the workflow's paths automatically builds a **stable**
release; promote beta fixes to main only when the maintainer requests it.

Update the user-facing `CHANGELOG.md` with the maintainer's local date and a
channel-specific heading (`YYYYMMDD-beta-description` or `YYYYMMDD-stable`).
Keep same-day stable and beta notes separate: the workflow filters them by
channel. Release version names are generated by the workflow and may use a
different date; report the actual published version instead of inventing one.

Verify the remote commit, Actions conclusion, GitHub Release channel and assets,
and application update metadata separately. A successful push is not a completed
build; a GitHub Release is not proof that the update server has synchronized.
Check the corresponding `/update.json` or `/update-beta.json` before claiming
application updates are available. Keep signing inputs ephemeral and redacted.

Close only issues whose requested change has been implemented and checked.
Record the release and validation boundary when closing; leave missing vendor
interfaces, absent playback metadata, and unverified player compatibility open.
Do not infer private broadcasts, package names, or provider contracts from a
product name. Prefer publisher documentation and reproducible diagnostics.

## Runtime and Performance Changes

Respect requests to ask before testing. Existing explicit authorization for
local tests, Lint, builds, release CI, or emulator checks remains valid for its
stated scope; do not ask for the same permission again. Real car/player and
physical multi-display acceptance are separate from emulator verification.

Settings may belong to a screen, a screen and style, or the whole application.
Use the shared preference helpers and preserve `DisplaySlotContext` isolation;
do not write a bare/global key for a screen-specific control. Performance
profiles should apply reversible runtime overrides rather than overwrite the
user's layout, font, colors, or individual effect preferences.

Recovery retries must stop when disabled, hidden, destroyed, or successful.
Use bounded delays instead of a finite boot-time attempt limit. Recover missing
windows without repeatedly rebuilding already attached screens. Keep bitmap
caches bounded, and do not recycle bitmaps still owned by another view or the
current music snapshot. Guard APIs newer than Android 4.4/API 19.

Keep existing copyright and license notices, including the separate licenses and
source attribution under `third_party/`. Read `LICENSE` and the relevant upstream
notice before adapting third-party code; do not replace those notices with the
project's default license text.
